Snapshot: 2026-10-16. This documents existing repository policy and decisions, not new approval to activate providers.

1. **Preserve the product:** R2NETTE remains a separate cleaning/reservation application with its own UI, branding and operational booking database. TAKATAK master identity is integrated only through approved tenant-scoped contracts; never place R2NETTE workflows inside the generic TAKATAK dashboard.
2. **Money:** The backend is the authority for service options, quote totals, GST/QST, discounts, products, frequency and payment state. Browser fields transmit user selections only. Stripe webhook receipts are validated server-side and live cards require complete provider configuration.
3. **Tenancy and personal data:** Customer and staff permissions are verified server-side, with individual staff sessions and least-privilege roles. Do not upload passwords, OTPs, card data, access/door codes or private notes into the TAKATAK bridge.
4. **TAKATAK sync:** Durable PostgreSQL outbox and signed delivery code is present in R2NETTE `main`. The remote receiver is gated by takatak-v1 PR #175 (open at snapshot). Until recipient is approved, released and signature-verified, `TAKATAK_R2NETTE_SYNC_ENABLED=false`.
5. **Publishing:** `main` CI must pass before GitHub Actions deploys SHA-tagged immutable images to Contabo. Deployer skips obsolete releases and verifies live health and readiness. DNS/email stay with MochaHost. No bypass of branch protections.
6. **Operator resilience:** Off-host backups, retention, encryption-key custody, tested restores and functional paging are launch criteria, not optional paperwork. Existing code may degrade safely when a provider is absent, but an unconfigured integration is never represented as live.
7. **Calendar exports:** Generate from a persisted booking, not from an unconfirmed hold; escape RFC 5545 TEXT values and fold long lines at 75 **UTF-8 octets** per physical line, without splitting multi-byte characters.
8. **Browser draft privacy:** Store only explicit allowlisted non-identifying service/property selections. Never persist street address text, private saved-address identifiers, customer identity/notes or held slot times in shared browser storage. Historical drafts must be sanitized on reading; completed bookings must not be restored.
9. **API error recovery:** Treat invalid JSON and HTML proxy error pages as safe typed API failures. Never render an upstream HTML response directly or hide an authoritative valid server error, including quote reprice data.
10. **Trusted proxy identity:** For per-client rate limiting and log client hashes, use Express `req.ip` with the approved immediate proxy trust (`TRUST_PROXY=true`, one hop). Never accept a raw, caller-controlled leftmost `X-Forwarded-For` address as an independent identity; test spoofed-prefix rejection.
11. **Fail-closed backup scheduling:** A daily job attempts at most once per Toronto calendar day even on failure, preventing repeated unverified dumps during an outage. A local-only database dump is retained but NEVER logged as a successful disaster-recovery backup: open an operational incident and record FAILED until a verified off-host copy succeeds. An unconfigured alert sink must not transform the failure into success.
12. **Subprocess secret protection:** Password-bearing PostgreSQL connection URLs must not be passed as `pg_dump` command-line arguments. Remove password from the URI and supply the decoded password only via the child process `PGPASSWORD` environment. Never log connection strings or that environment. PR #33 verified this change in production at `1c140ac1`.
13. **Remote backup integrity (PR #34 deployed):** A matching S3 object size is insufficient proof of recoverable data. Upload success requires HEAD size **and** streamed signed GET SHA-256 matching the local dump, without buffering the remote file. Fail closed on mismatch or download errors and retain the local copy; a provider must still be configured and real restore proved before production acceptance.
14. **Local fallback retention (PR #35 deployed):** After a fresh successful dump, prune expired local `r2nette-*.dump` regular files before any off-host upload failure can abort the run; never follow symlinks or delete unrelated files. The configurable `BACKUP_KEEP_DAYS` value must be an integer from 1 to 365. A failed pg_dump must not delete old fallback copies. CI and non-skipped Contabo deployment passed at `46fa61d3`.
15. **Bound alert delivery (PR #36 deployed):** Network calls to the operational webhook must have a short deadline so a stalled receiver does not indefinitely block a scheduled worker or its failure reporting. The alert persists in PostgreSQL with a FAILED delivery status on timeout; never misreport delivery as successful. Verified by main CI #38854383066 and non-skipped Deploy #38854525800 at `56cde1b6`.
16. **Memory-safe off-host uploads:** S3 single PUT must not read the entire PostgreSQL dump into Node heap. Hash incrementally first, then stream a signed request with the same payload digest and fixed size. A file larger than the 5 GiB single-PUT limit requires multipart support rather than a misleading success. Changes on `chatgpt/s3-stream-upload-20261016` are pending CI and actual rollout; keep the local dump on all upload failures.
17. **Shared VPS storage safety:** The deployment can clean up only obsolete R2NETTE SHA-tagged Docker images, never active, previous, target, other Coolify services or Docker volumes. Do not run global volume prune. Pre-pull cleanup is intended to recover from ENOSPC, with PR #39 CI and real deploy still pending.
18. **PGDMP dump validation:** Both scheduled and manual PostgreSQL backups must reject small or wrong-format dumps before off-host upload or local retention. Archive magic `PGDMP` and minimum size are a cheap integrity guard, not a verified restore. PR #38 remains pending deployment because shared VPS disk incident #40 is active.
19. **Agent continuity:**17. **Agent continuity:** Keep `AGENTS.md`, `WORKLOG.md` and the five `docs/` status files current; never claim a deployment or test without SHA-linked evidence. Avoid force-pushes and conflicting work.

19. **TAKATAK is the master account (2026-11-10, Claude — Anthropic):** customers sign in to R2NETTE with "Continuer avec TAKATAK" (OAuth 2.1 + PKCE, public client, server-side code exchange, UserInfo as the only identity source). R2NETTE keeps a copy and never takes over a historic profile by email match alone; linking an existing account happens from a signed-in session. Signup stays email-first; phone is imported only when TAKATAK already verified it and is otherwise requested after the first payment. Details: `docs/TAKATAK_INTEGRATION.md`.

20. **Sign-in stays on r2nette.ca (2026-11-11, Claude — Anthropic):** the customer signs in by email code or Google on r2nette.ca; TAKATAK sends the code, holds the account and decides consent, and R2NETTE shows TAKATAK's "Autoriser l’accès" card itself, then finishes through the same OAuth callback as decision 19 (same matching rules). The TAKATAK session token stays server-side, encrypted for at most 10 minutes, and is revoked after the decision. Details: `docs/TAKATAK_INTEGRATION.md`.

21. **Email code and Google only; the verified email claims the older profile (2026-11-12, Claude — Anthropic, owner order):** phone-number sign-in is off on r2nette.ca (`/phone-login`, `/verify`, `/profile` go to `/login`; `/api/v1/auth/phone/*`, `/auth/registration/*` and the phone-linked `/auth/google/*` answer 410 unless `R2NETTE_PHONE_LOGIN=true`). With no phone login left, the only way into an R2NETTE profile is a TAKATAK identity, so the address TAKATAK has just verified with a code now claims the existing profile carrying that email, unless another TAKATAK identity already owns it. Every older session of that profile is revoked at the claim. This replaces decision 19's rule that an email match alone never takes over a historic profile; that rule existed because a phone could still open the profile. A first-time customer accepts the terms on the consent card, not after a failed round trip. Details: `docs/TAKATAK_INTEGRATION.md`.

22. **The Autoriser l’accès card is shown on every sign-in; the Account link opens the account (2026-11-12, Claude — Anthropic, owner order):** after the emailed code (or Google) the customer always sees TAKATAK’s « Autoriser l’accès » card on r2nette.ca, then returns to the page they left. Before, a customer whom the hub already knew went straight through and never saw it. When the hub already holds the approval, R2NETTE keeps the finishing address it issued inside the encrypted consent cookie and still shows the card; Autoriser uses it, Refuser drops it. The header and mobile-menu « Account » link now go to `/account` (they went to `/auth`, the sign-in page, so a signed-in customer was asked to sign in again); `/auth` redirects to `/account`; the sign-in page sends an already-signed-in visitor on to `returnTo` or `/account`; the account page sends a signed-out visitor to `/login?returnTo=/account`. The wording of the code email is a hub setting (Supabase email templates) that this repository cannot change: `docs/HUB_EMAIL_PASTE.md`.
